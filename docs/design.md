# HQ design

## Identity and scope

The question key has three useful parts:

1. `directory` is the absolute, clean work dir at question creation.
2. `session_id` comes from `--session`, `HQ_SESSION`, or `CODEX_THREAD_ID`, in that order.
3. `id` is a UUIDv7 generated by HQ.

`HQ_SESSION` is the vendor-neutral session source. HQ also detects the Codex thread ID so Codex can use HQ with no extra setup. UUIDv7 gives IDs a creation-time prefix, while `created_at` and `id` give the database a clear sort order.

Bare `hq` checks both stdin and stdout. When both streams are terminals, HQ opens the TUI. Otherwise, HQ lists pending questions for the current work dir and inferred session. Without an inferred session, bare mode lists pending questions for all sessions in the current work dir.

## Storage contract

The `internal/store.Store` interface owns question creation, queries, state changes, and answer delivery. SQLite is the first implementation. A later server or shared database can implement the same interface.

The SQLite database uses:

- strict tables and explicit checks for state rules;
- WAL journaling;
- `synchronous=FULL`;
- foreign key checks;
- a five-second busy timeout;
- one connection per HQ process;
- indexes for scoped queues and answered rows;
- mode `0600` for the database and `0700` for its state dir.

The schema stores time as Unix milliseconds. The Go API exposes UTC `time.Time` values.

## Answer delivery

`answer` commits the response before an agent can read the response. `wait` and `poll` then follow these steps:

1. Atomically lease each answered, incomplete row.
2. Build the full output in memory.
3. Call stdout once.
4. Set `completed_at` and clear the lease.

The lease lasts 30 seconds if a process dies. SQLite and stdout cannot share one transaction, so a crash after step 3 and before step 4 can yield the same answer twice. HQ favors a retry over a lost answer.
